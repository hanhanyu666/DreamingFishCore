# 开服剧情使用 Java 流程与数据文案分离

## 背景

当前开服内容只有“梦的开始”个人选择和“余梦期”公开救治两条短流程。此前的通用
`story_flows.json` 把游标、条件、效果和迁移规则都编码成字符串图；一处文案或节点
调整往往还要同步游标别名、效果账本和任务镜像，导致维护成本高且容易产生重复发奖、
卡在错误节点等问题。旧服务器尚未运行这套新的章节状态文件，后续玩家数据可以由运营者
在停服备份后手工转换，因此没有必要继续在运行时猜测旧游标。

第二阶段的权威内容是《余梦期-逐光会公开救治》：公告、白芷私信、江晚复核、实际服药、
两天面具公告、再次交互领面具以及面具后的单人感染窗口都必须按明确顺序执行。

## 决策

1. 开服剧情转为按章节划分的 Java 状态机。`梦的开始`和`余梦期`各自拥有明确的
   状态枚举、事件入口和持久化对象；跨章节的世界阶段仍由 `StoryManager` 手动切换。
2. JSON/资源文件只保存可替换的玩家可见文案（对白、公告、私信和引导文字）。它们
   不再描述可执行节点、条件、效果或游标跳转；文案缺失时使用内置只读副本，坏文件
   不得覆盖原文件。
3. 运行时不再执行“旧 Flow → 新 Flow”的自动迁移，也不读取旧 Flow 游标别名。旧
   世界在切换前由运营者创建备份并按映射表手工修改；这项一次性运维工作不属于在线
   剧情代码。
4. 所有发奖、任务记录、公告发布和感染规则切换都采用显式、可重试的 Java 事务边界。
   状态只有在副作用成功后才前进；倒计时和感染治疗窗口使用 `因果式推进` 的在线
   活动 tick，并把截止 tick 持久化。
5. 使用 `StoryManager` 作为单一运行时协调入口，不保留旧 Flow 引擎的兼容门面。
   旧 Flow DTO、校验器和迁移器从活动源码中删除；未来若需要新内容，直接扩展对应的
   Java 章节状态机并新增测试。

## 后果

修改剧情顺序时，开发者只需修改对应章节的枚举和处理器，编译器会帮助发现遗漏的
`switch` 分支；修改台词时只改文案文件，不需要维护字符串游标图。每个章节的存档格式
更小、更容易人工检查，重复事件可以由布尔事实和一次性账本安全重试。代价是新增一个
真正的剧情分支需要改 Java 并发布模组，不能只编辑 JSON；这正是当前短流程换取可维护
性的取舍。

## 不在本决策中的事项

随机本线索、调查板、投票、复杂内容轮次快照和后续三至五阶段仍另行设计；它们不得通过
重新扩展通用 Flow DSL 来绕过本决策。
