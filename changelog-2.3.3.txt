刷怪箱改为创造模式专属（调整）
刷怪箱不再有合成配方，破坏后也不掉落任何东西（掉落表为空），只存在于创造模式物品栏。
它是服主布置尸潮玩法的工具，能合成或回收就会变成玩家囤积、搬运、重复刷奖励的道具。

组织职位改名与核心领地分级（新）
组织职位「副会长」改名为「管理员」：权重与权限完全不变（会长 > 管理员 > 干部 > 成员），
旧存档里存的 VICE_LEADER 会自动映射为管理员，不会因为改名被静默降级成成员。
组织领地新增「核心领地」分级：登记与标记只有会长与管理员能做（普通成员与干部不行）；
被标记为核心领地后，普通成员不能把它当作自己的场地或据点使用
（准入判定 OrganizationPermissions.canUseTerritoryAsVenue 已就位，供后续玩家场地系统直接调用）。
命令：/dreamingfish organization territory core <领地名或ID>，加 off 取消标记。
终端「组织」页里，会长与管理员在已登记领地上会看到「设为核心 / 取消核心」按钮，
核心领地带金色徽标；普通成员只看到徽标与「仅会长与管理员可用作场地」的说明，
拿不到按钮（权限位由服务端算好下发，界面只按开关画按钮）。
协议版本提升到 0.30.0（快照新增核心标记与权限位，旧客户端会被握手拒绝）。

随记本无法保存，导致线索记录丢失（修复）
此前随记本在加载时会自我死锁：读取玩家数据之后要做「旧整数编号迁移到稳定 ID」，
迁移内部标记玩家数据已变更，而那个标记会先校验「玩家数据是否已随世界加载」——
此时加载流程本身还没走完、标志位尚未置位，于是抛异常，被「读取失败」的兜底接住，
结果清空玩家缓存并把整个会话置为只读。表现为存档里再也写不进随记本内容
（日志反复出现「随记本玩家数据未安全加载，拒绝覆盖原文件」），
本次会话里发现的线索、解锁的成就等都无法记录。这个问题随稳定 ID 迁移一起引入。
现在把「读取失败」与「读取成功后的加工失败」分开处理：读取成功即落缓存并允许写盘，
迁移即使出错也只记日志、不再清空数据；加载路径内的脏标记也不再要求「已加载」。

尸体无法领取bug修复。
修复死亡结算时尸体所在区块未加载，导致复活后尸体永久停留在「待结算」、玩家无法领取的问题。

感染抑制剂（新）
新增两种药品：感染抑制剂（一次降低 5 点感染读数）与强效感染抑制剂（一次降低 15 点）。
两者不限制身份，幸存者与感染者都能服用；读数被压到 0 的那一下会一并解除感染者身份、
恢复为幸存者。注意这条规则意味着稳定感染者反复服用也能把读数刷到 0，从而绕开重构疗程
（这是明确选择的取舍，不是遗漏）。读数本来就是 0 且不是感染者时拒绝使用、也不消耗物品；
结算时若数值没有变化同样不消耗，避免白扔药。剂量数值集中定义在 InfectionRules，
身份变更走 InfectionTreatmentService.applyDoseSuppressant 这一条服务端入口。

随机丧尸线索掉落（新）
12 条线索正文随模组内置，首次开服写入 config/dreamingfishcore/data/clues.json（旧版 fragment_data.json 不再读取）。
随机掉落池、保底发放的存在性判定与调试命令现在全部走线索目录，不再读旧的片段文件；
旧的整数编号继续保留，用于兼容玩家手里已有的残页与旧存档里的收录记录。
被真人玩家击杀的普通丧尸（僵尸、尸壳）与攻城丧尸按概率掉落残页，概率与开关由
config/dreamingfishcore/clue_drop.json 控制（默认 0.01%，可整体关闭）。
玩家已收录的线索不再重复掉落，收齐后不再掉落。

二级感染的三次早期逆转疗程（新）
三次院内治疗，每次间隔 1 个剧情活动日（24,000 tick，仅在线累计），第三次之后终检清零并恢复为幸存者。
疗程结束后第 3 天与第 7 天由白芷发私信提醒随访，到医疗接待点与白芷当面交谈即完成复核。
逾期或漏做没有任何惩罚，只记录事实，不影响感染值与后续进度。

剧情地点改为按名称识别
阿拜多斯、逐光会/医疗接待点不再只认固定 ID：地点名称包含「阿拜多斯」「逐光会」「医疗接待」即会被剧情识别。
原有固定 ID 继续兼容；重建时若存在同名但随机 ID 的旧地点，会被自动替换（同名条目重复会导致地点配置加载失败）。

新增模组状态效果：感染 / 害怕 / 勇气
感染值过高 → 「感染」（移速 -15%、攻击力 -4，等同于原版缓慢 I + 虚弱 I）。
勇气值过低 → 「害怕」（数值同上）；勇气值高 → 「勇气」（攻击力 +3，等同于原版力量 I）。
不再借用原版效果，HUD 上能直接看出惩罚来自感染或恐惧，而不是某个药水。

玩家组织（自建公会）（新）
梦屿终端（U 键）新增「组织」页：创建组织、发布公告、查看成员、调整职位、离开与解散，全部由服务器判定。
组织名 2~12 字、单个组织最多 32 人、每个世界最多 64 个组织，都写在 config/dreamingfishcore/organization.json 里可调。
创建组织消耗梦鱼币（默认 150），解散时按当初实付的创建费退还一半（默认 50%）；
两项同样在上面那个配置文件里改，设为 0 即免费创建 / 解散不退款。
开会时钱先扣、存档写不进去就自动退款并取消创建，不会出现「钱花了组织没建起来」。
服务器未安装经济系统时不扣钱，创建与解散照常可用。
组织数据存在世界存档里，重启后自动加载；读档失败时进入只读保护，不会把存档覆盖成空的。
命令：/organization（别名 /org）。

关键线索的剧情保底发放（新）
01 / 04 / 08 / 11 四条关键线索不再只靠 0.01% 的概率掉落：01 在完成医院第一次正式复查时、
04 在完成二级感染三次疗程终检时、11 在感染者完成一次标准重建时，各发放一张绑定编号的残页；
形式与随机掉落一致，交到手里自己右键整理。
已经完成过对应事件的玩家会在登录时自动补发；08（外缘中继信号记录）等梁朔线展开后再接入。

线索系统的稳定 ID 与发放入口（新）
12 条线索的主键由「编号」升级为稳定 ID（dreamingfishcore:clue/<名称>），旧编号继续兼容并自动迁移，
已经收录过的记录不会因为改 ID 而丢失；残页物品与旧存档都同时认新旧两种绑定。
线索正文随模组内置；而「哪条是误导、哪条只是过度推论」这类揭示性内容改放在服务器私有文件
config/dreamingfishcore/clue_secrets.json，不进模组资源、也不会下发给客户端；该文件缺失时按
「无隐藏信息」正常跑，不会影响游玩。
随记本新增永久发现记录：线索只要见过就记下来（发放即视为发现），不再只有「已收录 / 未收录」两态。
发放统一收口到一个入口，拿不到就不再重复给（幂等）；并支持六种声明驱动的触发方式——
在私有文件里写 block= / container= / npc= / area= / broadcast= / event= 即可，
代码只认格式、不认识具体线索，所以改发放入口只需要改配置、不用重新编译。
触发时机：挖掉某方块、打开某容器、与某个 NPC 开始对话、进入某任务地点（写地点名或 ID 都认）、
读完某条公告、以及剧情事件点（目前有 hospital_review）。
命令：/dreamingfish clue info 查看目录规模；/dreamingfish clue reload 改完配置热重载、不用重启服务器；
/dreamingfish clue audit 做可达性审计，把「没有任何玩家走得到的入口」的线索直接点出来，
并报出声明格式写错（不会生效）与证据包里缺材料的情况。
第一个证据包已就位，主张是「观察区读数不下降，不等于痊愈，可能只是进入稳定期」，
四条材料按「短期真实观察（01 观察区值班记录）→ 过度推论（10 感染医学评审意见）→
稳定感染反例（11 重生节点异常记录）→ 可验证结果（04 康复者口述摘录）」排，
另有一条只挂主张不挂包的判据来源（02 逆转变异药剂使用说明：疗程 + 终检后读数清零）；
全部写在那份私有文件里，论证结构见 docs/CLUE_EVIDENCE_PACK.md。
人格同一性材料（03 隔离区外的字条、12 镇民口述）作为第二个证据包的待补内容保留。

合成蓝图（新，默认关闭）
玩家必须先学会某件物品的蓝图，才能在工作台里合成它。整套限制默认关闭，服主在
config/dreamingfishcore/blueprint.json 里把 enabled 打开才生效。
默认放行基础物品：木板、木棍、火把、工作台、熔炉、篝火、箱子，以及木制与石制工具；
其余物品（含所有装备、建材与机器）都需要蓝图。
蓝图由模组自定义丧尸（攻城丧尸）以 5% 掉落，且必须是玩家击杀；宝箱容器另有 25% 的掉落渠道。
丧尸渠道会排除击杀者已经学会的蓝图，不会掉重复的。
名单全部可配置且支持通配符（*_planks、minecraft:*_planks、wooden_?xe）：
defaultUnlockedItems（免蓝图）、exemptNamespaces（整个模组赦免，如让某个科技模组不受限）、
blueprintWhitelist（为空表示不限制）、blueprintBlacklist。
需要留意：黑名单只把物品挡在抽取池外，**并不放行**——被黑名单排除、又不在默认放行或
赦免命名空间里的物品将无法通过工作台合成（应当有别的获取途径），启动时会逐条点名警告。
命令：/dreamingfish blueprint info | pool | reload | give | learn | list | reset（2 级权限）。
顺带修掉两处旧问题：宝箱掉落渠道的"仅宝箱"判定把带玩家的容器战利品也筛掉了，实际上
从来不掉；终端里的"蓝图数量"用「已解锁总数 − 默认物品数」相减计算，默认名单改成规则后
这个减法会算错。

研究桌（新）
新增功能方块「研究桌」：右键打开界面，花经验一次性研究出一批原版配方，是蓝图的另一条获取途径。
一次研究默认消耗 100 点经验、给 10~15 个配方，都写在 config/dreamingfishcore/research_table.json 里。
只能研究出「需要蓝图、属于指定命名空间（默认只 minecraft）、且自己还没学会」的配方；
已经学会的会被跳过，不浪费经验。蓝图系统未启用时研究桌会自动说明原因并禁用研究按钮。
本次课题在打开界面时由服务端掷定并缓存，关掉再开还是同一批——避免反复开关刷随机结果；
结算全部在服务端，客户端只负责"我点了确认"。方块本身无状态、不需要方块实体。
配方：2 纸 + 1 书 + 5 木板（任意木材）+ 1 工作台。

感染身份状态机（新）
感染不再是「感染者 / 幸存者」两态，而是四种身份：幸存者、不稳定感染者、稳定感染者、传播复发。
身份仍由存档里的感染等级承载（0/1/2），传播复发是稳定感染者的临时状态，不会写成第三个等级。
存活者跨过感染阈值成为不稳定感染者；面具阶段的不稳定感染者有一整个游戏日的治疗窗口，
窗口关闭后突变就此稳定，成为稳定感染者。稳定感染者只有在重伤（单次实际损失 6 点生命以上）
时才会进入传播复发，复发持续 5 分钟后自动结束，结束后一段时间内不会再次触发。

野外传播改为「接触暴露」（行为变化）
在未受保护的区域靠近具有传播能力的感染者时，不再直接增加感染值，而是先累积「接触暴露」：
每 20 秒 +1 点（上限 6 点），并按 1 / 2 / 3 三档逐步给出警告；攒满后转化为一次 +8 点感染值增长，
之后重新累积。离开范围后每 20 秒 -1 点并逐档回落。
只有不稳定感染者与传播复发者会产生接触暴露——稳定感染者在正常状态下与幸存者正常相处
不会持续感染队友。防护面具仍然按原规则阻断传播来源（现在包含传播复发者）。
登出、死亡、重生与跨维度都会清空暴露量，不同维度之间也不会互相累积。
受伤折算顺带修掉一个老问题：/kill 一类来源会用 Float.MAX_VALUE 结算伤害，过去会按它折算成
"一次自杀直接涨满感染值"；现在单次伤害的折算上限是一整条血条。
（待接入：领地空气过滤/异常因子抑制设备按 ADR 0017 可以在自己范围内阻断被动传播，
该设备属于领地建设内容，尚未实装。）

污染适应与丧尸仇恨（新，软身份差异）
稳定感染者不再承受「感染」效果带来的移速与攻击力惩罚：突变稳定意味着身体已经适应异常因子。
普通丧尸把稳定感染者选为目标时，会优先转向更近的幸存者（24 格内）；找不到更近的幸存者时
有 60% 的概率直接放弃这个目标。幸存者、不稳定感染者与传播复发照常被仇恨。
尸潮丧尸正在执行声音/广播目标时不参与这套偏好，避免合围目标被路人改道。

重生代价按身份分档（数值变化）
幸存者 5 点、稳定感染者 10 点、不稳定感染者 20 点；保留物品栏的额外消耗仍为 30 点。
界面上的预览消耗与服务端扣费取自同一份数值表，不会再出现显示与实际不一致。
传播复发沿用稳定感染者的基础消耗。

分层治疗的服务端入口（新）
抑制剂（幸存者降低感染值）、早期逆转（不稳定感染者 → 幸存者）、稳定治疗（不稳定感染者 → 稳定感染者，
或结束传播复发）、高成本重构（稳定感染者 → 幸存者）四种动作现在共用同一个服务端入口，
身份变化一律由服务端校验、写入存档并同步客户端。
基因复苏试剂按此归类：未突变的居民属于足量抑制剂，不稳定感染者属于成本较低的早期逆转；
玩家实际服用后的结算以服务端最终判定为准。
按 ADR 0005，现有「三次疗程 + 终检」在代码里归为重构疗程（稳定感染者 → 幸存者）；
剧情文案里的「二级感染 / 三次早期逆转疗程」等叫法本轮不改，术语对齐留待剧情侧统一。

存档兼容
旧存档的感染等级语义不变（0/1/2 继续有效），因此不需要迁移脚本；读档时会清理
「身份不是稳定感染者却带着复发窗口」这类损坏数据。协议版本提升到 0.26.0，旧客户端会被拒绝连接。

已知边界
「重伤」是本轮唯一的传播复发触发条件；设定里的「高污染刺激」要等污染区域实装后接入。
复活护符的提示仍写作「感染者 / 幸存者」两态，属于剧情文案层，未随身份细化。

无头 gametest（新，开发期用）
感染状态机新增 7 个 gametest，用真实服务端玩家与真实丧尸覆盖单测够不到的部分：两名玩家同场的
传播规则（稳定感染者不感染队友、不稳定感染者会被扫到）、接触暴露攒满转化为感染、未认证会话
被拒绝、身份落盘后按真实加载路径重载、重伤触发复发并可由稳定治疗结束；以及丧尸仇恨的接线
（稳定感染者被选中时改投更近的幸存者，不稳定感染者不被降仇恨）。
运行：gradlew runGameTestServer（不需要客户端与人工操作）。
顺带：自定义载荷下发失败不再让服务端线程抛异常，而是记一条警告——这类失败过去会连带打断
触发它的登录流程或 tick 处理器。

组织与圈地联动（新）
组织的会长与副会长现在可以把自己名下的领地登记为「组织领地」：/organization territory 查看已登记
与可登记的领地，register/remove 登记与移除。本模组只保存登记引用，领地的所有权、成员、权限、
费用与持久化仍全部归经济模组（ADR 0035 明确禁止再建第二份私人领地数据）；每次展示与使用前都会
重新校验，领地消失或主人已退会时自动摘除。
组织新增资金池：任何成员都能捐款（/organization deposit <金额>，从自己的梦鱼币账户扣除），
余额只用于系统扣费、不提供取现入口；解散组织时余额全额退给会长，退款失败只记日志不阻塞解散。
新增方块「聚居地过滤装置」：放在本组织已登记的领地内，由会长/副会长右键绑定（再右键解除）。
设备每个维护周期（默认一个剧情活动日，仅在线累计）从组织资金池扣一次维护费（默认 20 梦鱼币）；
工作期间在半径内（默认 32 格，按 X/Z 水平距离、贯穿高度）阻断被动接触暴露——只阻断被动传播，
不治疗既有感染，也不阻止受伤、污染物与特殊袭击造成的感染（ADR 0017）。

射手僵尸（新）
新增远程丧尸变体「射手僵尸」（dreamingfishcore:archer_zombie）。它继承原版僵尸：近战追击、
开门、白天着火、水中腐化、原版模型与音效全部保留，只把生命值压到 16（低于原版僵尸的 20，
远程压制单位刻意更脆）、移速调到 0.21（原版 0.23），并额外增加了远程攻击。贴脸（2.5 格内）时
远程 AI 主动让位，交回原版近战，所以它仍然是一只普通僵尸，而不是站桩炮台。
远程 AI：与目标保持在 6~16 格之间——太近就后撤、太远就接近、在射程内站桩并横向游走；
视线通畅时按「蓄力抬手（22 tick，期间站定）→ 发射 → 固定冷却（40 tick）」的节奏循环，
抬手动作由同步状态驱动，客户端会看到它把双臂举起来。
骨刺投射物（dreamingfishcore:bone_spike）：飞行时有轻微下坠（每 tick 重力 0.045），
命中生物造成穿刺伤害（走自定义伤害类型 dreamingfishcore:bone_spike）并附加 3 秒「缓慢 I」
与 5 秒「流血」；命中方块或离开发射点 24 格后碎成骨屑消散。骨刺**不会伤害其他僵尸**
（同族免伤），尸潮里不会自相残杀。
骨刺伤害按**原版难度**缩放（和平/简单/普通/困难 = 0 / 0.75 / 1 / 1.5 倍，基础伤害 4 即
0 / 3 / 4 / 6 点）。这四个倍率写在 archer_zombie.json 里，可单独调。之所以为骨刺单独注册
伤害类型并声明 scaling: never，是因为原版 mob_projectile 自带一套硬编码的难度缩放
（简单 min(伤害/2+1, 伤害)、普通 ×1、困难 ×1.5），直接复用会让"按难度变化"变成隐式且不可调，
叠加自定义倍率还会变成双倍变化。死亡提示：death.attack.bone_spike[.player]。
流血（dreamingfishcore:bleeding）：每秒结算 1 + 等级点穿透护甲伤害，走自定义伤害类型
dreamingfishcore:bleeding（死亡提示「失血过多」）。**对玩家而言只有在移动中才结算**——
结算那一 tick 必须有 WASD 级别的水平位移（位移信号由 PlayerMotionTracker 在
PlayerTickEvent.Post 采样上一 tick 的位移得到，因为原版的 tickEffects() 跑在移动之前，
当场现算永远是 0）；站着不动等于压迫止血，但效果本身不会提前消失，一走又开始掉。
非玩家生物（村民、动物）不受这条限制，照常每秒结算。
音效：新增 entity.archer_zombie.charge / shoot 与 entity.bone_spike.hit 三个事件，
音源以 sounds.json 的 event 别名复用原版音效（僵尸低吼 / 破空 / 命中），资源包可直接覆盖。
资源：占位皮肤 textures/entity/archer_zombie/archer_zombie.png（复制自围攻僵尸皮肤，
换正式美术只需替换该文件）、骨刺贴图与流血图标均为代码生成的占位资源。
自然生成：射手僵尸不新增独立条目，而是从「自定义丧尸」的权重里再切一刀
（archer_zombie.json 的 spawnPercentOfCustomZombie，默认 40%，即原版 40 : 围攻 36 : 射手 24，
僵尸家族总权重不变、原版僵尸比例不变）；把它设为 0 即完全退回改动前的行为。
数值配置：config/dreamingfishcore/archer_zombie.json，写入即生效，改完用
/dreamingfish zombie reload 热重载（同时重载围攻僵尸配置）；/dreamingfish zombie status
会打印当前全部射手数值（伤害、难度倍率、射程、间隔、弹速、生成权重等）。所有字段都有范围校验，
写坏的配置会被拒绝并保留上一份有效值，不会进到正在跑的 AI 里。注意配置文件优先于代码默认值：
升级已有服务器时请删掉旧的 archer_zombie.json 让它按新默认重建（或手动改 maxHealth）。
蓝图掉落：射手僵尸与围攻僵尸一样，被玩家击杀时按 blueprint.json 的
siegeZombieDropPercent 抽蓝图（「模组丧尸家族」统一由 ModZombieSpecies 标记接口判定）。
验证：`gradlew compileJava` 通过；`gradlew test` 517 用例全绿（新增 17 条：配置校验、
难度倍率映射与逐档覆盖、生成权重三分法的守恒/单调性质、贴图与 sounds.json 一致性）；
`gradlew runGameTestServer` 全部 19 条 required gametest 通过，新增 6 条覆盖
「AI 锁定玩家并在射程内开火」「骨刺命中造成伤害 + 减速 + 流血 + 消散」「属性与掉落表沿用原版僵尸」
「骨刺伤害等于基础伤害 × 当前难度倍率」「流血在静止时不结算、移动时结算」「模拟玩家可被骨刺伤害」。

焦尸（新）
新增变体「焦尸」（dreamingfishcore:charred_zombie）：只受火焰类伤害的僵尸。继承原版僵尸，
近战追击、开门、破门、装备随机生成、水中腐化全部保留，差异在属性（生命 22、移速 0.20、
索敌仍为 35）与一条核心规则上——非火焰类伤害在扣血前被归零。
伤害闸门：火焰类伤害照常结算，判定用原版 minecraft:is_fire 标签，并额外纳入烈焰人与恶魂的
火球（minecraft:fireball / minecraft:unattributed_fireball，它们不在原版标签里）；其余伤害一律归零。
归零不等于无事发生：受伤动画、击退、仇恨、武器耐久消耗、附魔点火全部保留。实现上刻意**不**在
hurt 里提前 return false，而是把这次伤害压到 0 再交给原版流程——因为火焰附加的点燃挂在
Player#attack 里 EnchantmentHelper.doPostAttackEffects(...) 的调用条件（if (target.hurt(...))）上，
返回 false 会让「用火剑点火」这条最顺手的反制路径直接失效（而火矢的点燃在 hurt 之前无条件执行，
两条路径会变得不一致，很容易被当成 bug 报上来）。免疫命中时会喷灰烬粒子并播出 block.fire.extinguish
作为反馈，因此**没有**新增 sounds.json 条目。
易燃体质：受到的火焰类伤害 ×2（fireDamageMultiplier），且着火期间移速 +15%、攻击力 +2
（burningBoostEnabled / burningSpeedBonus / burningAttackBonus）——用火是双刃剑，点火的人要承担它变凶的代价。
易损：被火焰类伤害命中后附加新效果 dreamingfishcore:vulnerable「易损」（默认 100 tick = 5 秒）。
期间 ① 非火伤害不再被归零（破防），② 所有伤害按 1 + 10% × 等级 放大。等级按原版口径换算，
amplifier 0 就是 I 级 = +10%（不是 +0%）；易损期间焦尸会发光，给玩家「它现在打得动了」的可读信号。
本次命中只结算火伤、不享受自己打出的易损加成，下一次命中才开始破防，避免自我放大。
环境行为：白天不再自燃（burnInDaylight 默认 false）——日光燃烧走的是 on_fire 伤害类型，也就是
免费的火焰伤害，保留它等于让玩家靠等天亮就能破解「必须用火」这条机制；泡水 600 tick 仍会腐化成
溺尸（convertInWater 默认 true），当作「水把它浇灭了」的收场，也给玩家留了一条处理它的路。
兜底通道：虚空/溺水/摔落默认始终有效（alwaysEffectiveDamageTypes），不吃免疫也不吃倍率，避免出现
一旦卡位就只能靠 OP 命令清理的怪；把该数组清空即变成「除了火谁也弄不死」的硬核版本。
资源：占位皮肤 textures/entity/charred_zombie/charred_zombie.png（原版僵尸皮肤炭化版）、余烬眼睛层
charred_zombie_eyes.png（走 RenderType.eyes 全亮叠加，只亮两个眼睛像素）、易损图标
textures/mob_effect/vulnerable.png，均可在替换正式美术后直接覆盖。
生成：本版**不接入自然生成**（不改刷怪池、不注册生成位置规则），只提供创造栏刷怪蛋与 /summon；
/dreamingfish zombie status 会打印焦尸的全部当前数值，/dreamingfish zombie reload 一并热重载。
数值配置：config/dreamingfishcore/charred_zombie.json，写入即生效，所有字段有范围校验，
写坏的配置会被拒绝并保留上一份有效值；配置文件优先于代码默认值，升级已有存档时按需删旧重建。
验证：`gradlew test` 542 用例全绿（新增 25：伤害闸门判定表、倍率与等级换算的单调性、配置默认值/
校验/坏值拒绝、贴图与语言键一致性）；`gradlew runGameTestServer` 全部 24 条 required gametest 通过，
新增 5 条覆盖「非火伤害不掉血但命中必须生效」「火焰伤害被易燃体质放大成 2 倍并打出易损」

水枪装水修复（实机反馈）
现象：游戏里对着水面右键装不上水（水量不涨、量条不动），反而喷了自己一身。
根因有两个，都不在「装水逻辑」本身，而在它两侧：

1) 水源根本认不出来。原版选方块走 ClipContext.Block.OUTLINE，而 LiquidBlock#getShape(...) 返回
   Shapes.empty()——水方块没有轮廓形状、准星选不中它，射线直接穿水而过打在水底的地面上。
   于是 useOn 收到的 clickedPos 是沙子/泥土，state.getFluidState() 恒为 EMPTY，判定永远不成立，
   返回 PASS 之后原版就落到「喷自己」上。
   修法：新增 Item_WaterGun#findWaterSource，改用 ClipContext.Fluid.WATER 单独做一次带流体的射线
   （该模式下水流体是有形状的，能被命中），长度取玩家的方块触及距离。装水的判定只保留这一份：
   useOn 里只额外处理「水瓶炼药锅」这一个例外（锅里的水不是流体方块，流体射线看不到它），
   其余（含水方块、普通水）都交给它；useOn 返回 PASS 后原版会接着走 use，那里也调同一个方法，
   所以「对着水面右键」的两条入口（命中方块 / 射线 MISS）都能装水。

2) 装上了也看不见。原版只有 ServerPlayerGameMode#useItem 会顺手调
   inventoryMenu.sendAllDataToRemote()；useOn 这条路径全程没有物品同步，左键射水走的又是自定义
   网络包，原版根本不知道。不补这一步，服务端水量变了而客户端的 ItemStack 组件还是旧的，
   物品栏那条量条与 tooltip 会一直停在装水前的数字，玩家会当成「压根没装上」。
   修法：新增 Item_WaterGun#syncWater(player)，在装水成功与 fireJet 成功后各同步一次。

为什么之前没测出来（教训）：原来那条 gametest 用手工 new 出来的 BlockHitResult 直接指定水方块坐标
去调 useOn，等于把真实的射线入口整个旁路掉了——逻辑是绿的、游戏里是坏的。现在改成用 level.clip
算出的真实命中点去构造上下文，并新增一条守护事实的用例 vanillaBlockRaycastPassesThroughWater
（断言原版方块射线不会把水方块当作命中目标、带流体的射线才会命中）。反向对照做过：把
findWaterSource 临时改成恒返回 null 后，正是那两条装水用例变红。

另有一个测试环境的坑一并记下：给玩家摆朝向时只调 setYRot 是没用的——LivingEntity 覆写了
getViewYRot 取 yHeadRot，而 Entity#getViewVector 是 final 的、会走那个覆写；pitch 没有这层覆写
所以照常生效。表现为「低头角度对了、水平方向完全没转」。要一起调 setYHeadRot。

验证：`gradlew test` 577 用例 0 失败；`gradlew runGameTestServer` 全部 35 条 required gametest 通过
（33 → 35：原「对水源右键装满」1 条替换为 3 条，净增 2）。

美术：水枪物品贴图换成正式美术（16x16 RGBA，原图 C:\叽叽团\工程\纹理\watergun_16x16.png），
替换原先脚本生成的占位图；模型引用不变（item/handheld + dreamingfishcore:item/water_gun），
物品模型与资源一致性测试（7 条）全绿。随后按第一人称手持观感，贴图换成其水平镜像版
（枪口朝左，逐像素 256/256 与原图镜像一致）。

射手僵尸换成自制模型（新）
射手僵尸改用作者自制的 Blockbench 工程（azombie.bbmodel）：16 个立方体（6 个人形盒 + 10 个枪械
部件），骨骼原点与原版僵尸模板对齐。几何由 tools/convert_archer_zombie.py 生成 Java 模型代码；
Bedrock 坐标与原版的换算是 (x, 24-y, -z)，即「绕 x 轴 180° 的纯旋转」，所以旋转角按「x 保持、
y/z 取反」映射；带自身旋转的立方体提升为子骨骼（原版 CubeListBuilder 不支持立方体自转）。
两个动画（walk / shoot）转成 NeoForge 动画 JSON 放在 neoforge/animations/entity/archer_zombie/，
改动画只需重导 JSON + F3+T，不用编译。贴图从 bbmodel 内嵌图烘焙（80/96 个面与标准 box UV 展开
逐像素一致；16 个底面因标准位置被占用而留空，均朝下或朝内，正常视角看不到）。
蓄力时长随之从 22 tick 调整为 16 tick 与 shoot 动画（0.8 秒）对齐，抬手完全交给动画，原先的
程序化抬手代码已删除。改几何需重跑脚本并重启客户端。

修复：射手僵尸头顶永久显示自己的名字（看起来像被命名牌命名过）
根因是渲染器父类选错。原版 MobRenderer 覆写了 shouldShowName，要求「实体名字常显，或有自定义
名字且准星正对着它」；而 LivingEntityRenderer#shouldShowName 只判距离与可见性、完全不看实体
有没有名字，于是每只怪头上都会永久顶着自己的名字。当初为了让自定义骨骼不受原版盔甲层错位影响，
父类从 AbstractZombieRenderer 改成了 LivingEntityRenderer，顺带丢掉了这层判定。
改为继承 MobRenderer：它本身不追加任何层（盔甲层是 AbstractZombieRenderer 加的），既避开盔甲
错位，又保留原版名牌规则。其余三个僵尸变体一直走 AbstractZombieRenderer，所以没有这个问题。

修复：射手僵尸「背身开枪」+「说是站定却一直往前挪」
两个原版机制没处理对，一起修：
1) 停机用错了 API。原版 PathNavigation#stop() 只把 path 置空，moveControl 上一次留下的移动输入
   （zza/xxa）原封不动 —— 而 Mob#setSpeed(speed) 会顺手把 zza 设成 speed。所以蓄力期间的「站定」
   实际上是保持原速继续往前走。改用 Mob#stopInPlace()（speed 与移动输入一起归零），并在蓄力
   期间每 tick 维持。
2) 站定后没有自己转身。原版 BodyRotationControl 在**移动中**会把 yBodyRot 直接设成 mob.getYRot()
   （= 上一次的行进方向），而 getYRot() 只有寻路才会被改；头又只能在 getMaxHeadYRot()（75°）内偏。
   于是它身子朝着旧方向、头最多扭 75°、骨刺却按数学精确命中 —— 表现就是「背身射我」。
   现在站定与蓄力时显式把 yRot / yBodyRot 以 30 度/tick 转向目标（蓄力 16 tick 足够转满 180°）。
一并调整：
- 站桩时不再横向侧移。原实现用 MoveControl#strafe，它把 speedModifier 写死 0.25（每秒只挪约 1 格）
  且完全不碰 getYRot()，是「走路诡异」的另一半原因。现在改为干净的站定瞄准。
- 射程内但视线被墙挡住时会去接近（原来「射程内一律站桩」会卡在墙后干等，永远打不着）。
- 走路动画驱动系数改为与原版 HumanoidModel 一致（animateWalk 的 2.0F / 2.5F）：原来配的是
  1.0F / 2.0F，腿摆得比实际移动慢，看上去像在滑步。
- 转换脚本修正动画 position 通道的 z 符号：NeoForge 的 KeyframeAnimations.posVec 自带 y 取反
  （new Vector3f(x, -y, z)），所以只有 z 需要我们自己翻。射击动画里身体后仰的位移原来方向是反的。
关于「骨块左右反了」：核对过模型的 6 个人形部件（body / head / left_arm / right_arm / left_leg /
right_leg）的 box 与 pivot 数值，与原版 HumanoidModel **逐字节一致**，因此模型本身不可能左右镜像；
枪件是 right_arm 的子部件、x 比骨骼枢轴更负（同侧外侧）。看到的「反了」是身体朝向错误导致的错觉，
随上面第 1、2 条一并修复。

美术调整：右臂上 3 个大块的贴图左右镜像
缠在右臂上的 3 个大块（6x2x6、6x2x6、5x4x6 —— 把 4x4 的手臂整圈包住的那几块）贴图改为左右翻转。
实现用 CubeListBuilder#mirror()：原版语义是「只交换盒子的 x 两端 + 反转 UV 顶点顺序 + 法线 x 取反」，
也就是**几何原地不动、贴图左右镜像**——这几块左右本来就对称，所以灰模完全看不出差别，只有贴图能看出来。
转换脚本里的判据写成「父骨骼是 right_arm 且 x、z 尺寸都 >= 5」，不用 uuid（重导模型后 uuid 会变，
写死会静默失效）。
说明：核过源模型 16 个部件的非底面 UV，全部匹配标准（未镜像）box 布局，原版 HumanoidModel 的右臂也
没有使用 mirror() —— 所以这是一次美术取向的调整，不是转换脚本的漏项。想还原只需去掉脚本里那条判据。

资料库（新方块）
新增功能方块「资料库」（dreamingfishcore:archive；合成：纸 / 书 / 书架 / 木板）。
它是一个配方共享点：谁把自己学会的配方存进去，后来的人左键就能免费学会。
- **右键 = 存入**：把「自己已解锁、且确实需要蓝图」的配方一次性并入该方块，聊天栏回显本次新增条数
  与库中总条数；重复存入不会产生重复条目；免蓝图的物品不会被收（它们本来就能合成，存进去没意义）。
- **左键 = 学习**：一次性学会库里自己还没学会的全部配方。**库内容不消耗** —— 同一座库可以被任意多人
  反复学；库里已经全都会了会明确提示「都已经学会了」，而不是静默无事发生。
- **潜行 + 左键 = 原版挖掘**：否则方块放下去就拆不掉了。不潜行时左键一律拦截（哪怕库是空的），
  这样「不潜行 = 不会挖掉」这条规则是单一点的，不会出现「能不能拆取决于库里有没有东西」。
- 权限：任何人都能存也能学（就是个公共图书馆），不做放置者限制。
- 内容存世界存档的 data/dreamingfishcore/libraries.json，按「维度|X|Y|Z」索引；沿用了刷怪箱那套
  原子写 + schemaVersion 校验 + 读档失败进只读保护（绝不用空表覆盖存档）。
- **方块本身不带方块实体**：本模组所有需要持久化的方块状态都放服务端注册表（刷怪箱、聚居地过滤
  装置同理）——服务端才能一次遍历，也白拿了原子写与只读保护。
- **左键走 NeoForge 的 PlayerInteractEvent.LeftClickBlock**（服务端可取消），所以**没有任何客户端
  代码**，也就没有「客户端与服务端谁说了算」的问题；两侧都取消是为了不让客户端起挖掘动画。
- 蓝图总开关关闭时不需要特殊分支：isExemptFromBlueprint 一律放行 → 「已解锁且需要蓝图」恒为空 →
  库天然是空的，右键会给一句「蓝图系统未启用，所有配方本来就能直接合成」的说明。
- 贴图是脚本生成的 16x16 占位资源（木框 + 三排索引卡片抽屉），换正式美术只需替换同名 PNG。

尸潮指挥官（新 Boss）
新增远程 Boss「尸潮指挥官」（dreamingfishcore:zombie_commander）与它召唤的「尸潮护卫」
（dreamingfishcore:commander_minion）——本模组的第一个 Boss。它沿用原版僵尸的骨架，另做了一套
「走位 → 有预警的施法 → 连发/召唤 → 冷却」的战斗循环，全部结算在服务端。
- 出现方式：不接入自然生成，只提供创造栏刷怪蛋与 /summon。Boss 随机刷在野图会直接打乱普通玩家的
  生存节奏，交给服主或剧情按需放置更合适。
- 两阶段：生命降到配置阈值（默认 50%）进入狂暴——头顶 Boss 条由紫转红、名字加上「狂暴的」前缀，
  攻击间隔 2.5 秒 → 1.5 秒、每轮弹数 3 → 5、召唤数 2 → 3，并立刻缩短召唤冷却。
- 远程连发：与目标保持在 8~24 格之间（太近后退、视线被墙挡住就去接近、射程内站定并转身），
  蓄力 24 tick（1.2 秒：站定 + 转向目标 + 灵魂粒子预警）后连发 3 发骨刺，弹间隔 6 tick；
  贴到 2.5 格内还有一次近战反击（30 tick 一次），不会因为永远后撤而彻底失去攻击手段。
- 召唤：每 20 秒一次、蓄力 2 秒，每次 2 只护卫（狂暴 3 只），同时存活上限 6 只；护卫有 60 秒寿命、
  会继承 Boss 的当前目标，Boss 阵亡或消失时一起清掉，不会变成野怪。
- 护卫台账保留「未加载区块」里的配额，否则把 Boss 拖远再回来就能无限刷兵；但**区块还加载着却找不到
  实体**（护卫被打死或被清理）时必须把名额还回来——这条曾经漏掉，会让护卫阵亡后名额被一个不存在的
  实体占着，最长空占满 60 秒。
- 弹丸：复用射手僵尸的骨刺模型、命中判定与同族免伤，但伤害与难度倍率走 Boss 自己的配置
  （倍率在弹丸创建时快照进 NBT，不受射手僵尸配置影响）。
- 掉落：显式沿用原版僵尸战利品表。不写这一条的话，EntityType 会按注册名推出一张
  dreamingfishcore:entities/zombie_commander 的表，而它并不存在——Boss 打死了什么都不掉。
- 蓄力特效（全部是原版粒子，不新增任何资源）：骨刺蓄力是一套三段式的「充能」读条 ——
  外圈灵魂粒子一边向内收拢一边抬升（半径随进度从 2.5 收到 0.45），粒子从青色的 SOUL 换成更冷的
  SCULK_SOUL、最后一段再换成 ELECTRIC_SPARK，玩家不看血条也能读出它充到第几成；过半后眼睛处持续
  冒 SOUL_FIRE_FLAME，濒临发射时贴着身体闪一层 ENCHANTED_HIT。蓄满那一刻放一次 SONIC_BOOM 音爆环
  加向外炸开的 END_ROD（每轮仅一次，不吵），连发每发再补一小簇枪口闪光让节奏看得见；召唤收尾是
  一次 TOTEM_OF_UNDYING 金色脉冲。狂暴态下外圈半径与粒子体积都会加大。

  低配机或集显可以直接关掉，不影响任何战斗结算。

尸潮指挥官现在有自己的战斗音乐。触发规则：靠近到 48 格内起播，18 格内满音量、到 48 格线性归零，
Boss 阵亡或玩家走远都是淡出而不是硬切；音源挂在「音乐」音量滑块下，可以单独调。
起播前会停掉原版背景音乐，避免两首叠在一起（原版 MusicManager 自己会重新计时，通常十几分钟后
才会想再放，所以只停这一次就够）。
曲子是 A 小调、104 BPM、32 小节（约 74 秒）的可循环段落，和声走 Am - F - Dm - E（i - VI - iv - V；
E 大和弦里的 G# 是 A 和声小调的导音，也是整首紧张感的来源），结构是
「引子（次低频暗流 + 定音鼓心跳 + 远处铜钹，鼓组刻意不进场）→ 底鼓/踩镲/军鼓齐入 + 低音八分行进 →
主题第一次陈述 → 主题碎片化成小二度摇摆 + 弦乐十六分脉冲、踩镲转十六分 → 全奏收束接回循环」。

主题的取向（第二版重写）：最初那版旋律是"能唱"的 —— 稳定的音高中心 + 上行乐句，结果听感偏激昂、
甚至欢快（音域 C5-E6、平均 G#5，18% 的音在 1047Hz 以上，最高到 E6 = 1319Hz，正好是小号最嘹亮的音区）。
整条重写成"敲"而不是"唱"：大量同音反复（13 处）、半音级进（占相邻音程的 59%），并在 E 和弦上硬顶
根音上方小二度的 F。C 段也不再走高八度变奏，改成小二度来回摇摆的碎片化动机。

编制换成电子（第三版）：第二版虽然把音区压下来了，主奏仍是铜管，听感"出戏"—— 参照对象不是管弦乐而是
Pigstep。把那首的 MIDI 拆开看得很清楚：它的低音由 Trombone(平均 D2) + Tuba(平均 G#1) + 失真吉他
(平均 F2) 三层叠成墙，而**旋律其实是长笛 + 单簧管**（D#4-C5），另外还有一条 Muted Trumpet 轨
128 个音**全是同一个 A3**、从头到尾不动。据此重做配器：

  * 主题改长笛（锐化版），音区 E4-F5；
  * 低音换成失真锯齿（谐波按 1/n 铺满，又厚又脏）+ 次低频暗流 + 管风琴，三层叠成墙；
  * 新增一条全曲不动的 A3 踏板音（单簧管音色，空木质感），对应原曲那条 Muted Trumpet；
  * 和声垫音量从 0.105 退到 0.055，把中音区让给旋律和踏板；段落交界的不谐和音簇也换成单簧管；
  * 踩镲改成全曲十六分（445 个事件），铜钹只留 3 处；
  * 混响从 0.30 收到 0.12 —— 大混响会立刻把电子编制拉回"管弦大厅"。

旋律按东方的音程分布重写（第五版）：拿 U.N.オーエンは彼女なのか？的 MIDI 做实测对照
（工具：tools/analyze_midi.py），它的旋律是「小跳(3-5 半音) 56% / 大跳(≥6) 19% / 同音 13% /
级进 12%，平均 |跳进| 4.8 半音」；我们第四版是「级进 42% / 大跳 4% / 平均 2.8」—— 太平滑，
所以"不够硌"。重写后：**小跳 82% / 大跳 14% / 级进 5%，平均 |跳进| 4.4 半音**。

同时抄了东方的两个要素：
  * **滑音装饰**：原曲那条旋律轨有 114 次 pitch bend。合成器里加了起音滑音（35ms 内
    从下方 60 音分滑到目标音），用**相位累积**实现而不是 f*t，否则频率一变相位就断、会咔哒。
  * **低音墙**：东方快曲的低音普遍压在 F#1-A#2（46-116Hz）。给低音轨加了一条降八度的副本
    （A1-D1）一起渲染，低音从"一条线"变成"一堵墙"。MIDI 里也补了对应的 BassLow 轨（19 轨）。
  * 开镲从 3 处加到 11 处（U.N. 的 OpenHat 有 235 个，它把开镲当主要 hi-hat 在用）。

关于「神さびた古戦場 ～ Suwa Foughten Field」（風神録 6 面 BOSS 曲）的参照分析（试过又退回）：拆开它的 MIDI 后有四个发现，其中三项做了实验但**听感不如原版，已全部回退**——记在这里是为了
下次不再重复试：

  * 它是 **3/4 拍**（168 BPM），这是它"旋转式推进"的根源。我们是 4/4，改拍号等于整首重来。
  * 它的低音轨平均 |跳进| 8.5 半音、大跳占 56%（低音在那儿是推进力而不是伴奏）。照做改成在
    根音 / 低八度 / 上五度之间跳（实测 9.6 半音）——**听感变浮，低音失去落点，整首像踩在棉花上**，
    已回退。结论：低音的跳跃程度是风格选择，不是越高越对，这首曲子需要一根稳的锚。
  * 它用了 433 个 Splash 水镲，但那是配 3/4 拍 + 168BPM 的；搬到我们的 4/4 / 104BPM 里只显得吵，
    已回退。统计数字相似 ≠ 听感相同，配器要连着拍号与速度一起看。
  * Kick 加密（110 → 133）同样已回退。

最终保留的是上一版的骨架：低音平均跳进 2.2 半音、主题 154 音 / 平均跳进 4.4 半音。

第七版（换乐器 + 学它的节奏）：

  * **主奏换成小号 + 小提琴齐奏**。原曲那两轨（Trumpet / Violin）的音符数、音域、时值分布逐项
    一致，是一条旋律线叠两件乐器——照做。长笛随之删掉。
  * **节奏学它的附点**：B 段与 D 段每拍拆成「长 0.70 + 短 0.20」（38 对），不再用均匀八分。
    那种"长—短"的摇摆是它区别于"哒哒哒"均匀行进的关键。
  * **琶音层从只盖 C 段扩到全曲**：原曲有一整轨 Steel Guitar，659 个音全部是 0.25 拍——均匀十六分
    的分解和弦铺底。我们的 PULSE 轨照此从 128 音扩到 448 音。

第七版实测：mean −17.4dB / max −1.7dB 未削波；>2kHz −32.2dB（小号比长笛亮 3dB）；MIDI 20 轨。

第八版（换成高速钢琴）：主奏从小号 + 小提琴换成**钢琴**，背景那层十六分也改成钢琴。

  * 钢琴音色：谐波铺到 8 次，包络 `0.004 / 0.40 / 0.22 / 0.15` —— 靠"4ms 起音 + 长衰减 +
    极低保持值"做出击弦的颗粒感。钢琴没有真正的 sustain，保持值给 0.22 才是"敲一下就走"的听感。
    钢琴不加滑音也不加失谐：它靠颗粒感立住，加了反而糊。
  * 琶音层音高做**"两上两下"的八度摆动**（每拍前两个音高一档、后两个落回来），音域摊成 D3-E5。
    一开始是整层 +12 吊在 A4-E5，但主奏本来就在 E4-F5，两层挤在同一个八度只会互相掩蔽。
  * MIDI 从 20 轨回到 19 轨（两条主题轨合回一条）。

第八版实测：mean −17.5dB / max −1.4dB 未削波；>2kHz −33.8dB（钢琴介于长笛与小号之间）、
1-4kHz −29.6dB。主题与琶音的重叠音区从"几乎全叠"收窄到 E4-E5。

第九版（去掉"诡异"、换成"刺激"）：反馈是"后面的调子太诡异了，我想要刺激的"。定位到三处元凶，
都在后半段起作用 ——

  * **段落交界的强击原来是「根音 + 五度 + 上方小二度」**，那个小二度就是"诡异"本身。改成
    纯五度 + 八度的堆叠（power chord），同一位置从"不适"变成"威武"。实测音程集合从含 ±1 变成
    只剩 [5, 7, 12]。**诡异和热血的差别，就卡在这一个半音上。**
  * **张力长音 TENSION 停用**：每个和弦挂一个不解决的和弦外音，那是"不安"而不是"压迫"。
  * **踏板音 PEDAL 停用**：全曲钉死一个不动的 A3 —— 那是氛围音乐的手法，不是战斗音乐。
  * **D 段从附点长音改成密集跑动冲刺**（十六分 + 八分一路往上冲），收尾不再"沉下去"。

第九版实测：mean −18.9dB（删掉两个声部后比上版低 1.4dB）/ max −1.5dB 未削波；MIDI 19 → 17 轨。
TENSION / PEDAL 的定义仍留在脚本里并标注了停用原因，想恢复把声部加回 body 即可。

第十版（后半段重写）：反馈是"没变化感觉，后半段重新写试试"。一量就找到了病根 ——

**原来的 C/D 段和 B 段走的是同一个八度**（都是 E4-F5，平均 D5），前后半段没有任何音区落差，
听感自然"没变化"。重写后：

  * C 段（21-28）整体抬到 **A4-B5（440-988Hz）**，平均 E5。每小节前半是一串上行十六分冲刺
    （A4-C5-E5-A5）冲到高音站住，后半落回来，每两小节一轮，第 8 小节顶到 B5。
  * D 段（29-32）**整段停在 A5 附近不下来**，用「A5 → 五度下落 → 回冲」的型推着走，
    最后一小节连续上行顶到 B5 接回循环。
  * 全曲最高音 698Hz → **988Hz**；后半段平均比前半段高 5~6 个半音。

实测：mean −18.9dB / max −1.5dB 未削波；响度从 20s 的 −20.0dB 爬到 66s 的 −17.5dB，
有了 2.5dB 的"上台阶"。

第五版的完整快照（脚本 + ogg + mid）存在 `tools/archive/v5/`，随时可以对照或回退。

仍未解决的一个差距：我们的同音比例是 0%，U.N. 有 13%——那 13% 是它"哒哒哒"的敲击感来源，
想补的话是在 riff 里插重复音。

打击乐分五件、按段落逐层加密：底鼓（正拍与定音鼓齐奏，B/C 段补切分）、踩镲（八分转十六分，
每 8 小节开一次镲）、军鼓（A 段起打后拍，B/C 段加 ghost note）、通鼓（段落交界前一小节的第 4 拍
走四音过门）、铜钹（段落交界）。定音鼓在 D 段心跳翻倍成每拍一下——同样的鼓、同样的音高，
只是越来越快，这比加任何新乐器都更能把"该结束了"的压力堆上去。

压迫感是四层叠出来的：① 上面这套逐层加密的鼓组；② 全曲一条 55Hz 的次低频暗流（归一化时被排除在外，
避免它把其余部分一起压扁）；③ 每个和弦块挂一个不解决的张力长音（E 上那个与根音只差小二度的
F 最狠——它不给任何解决的余地）；④ 低音线的半音逼近、段落交界的不谐和音簇强奏（根音 + 纯五度 +
上方小二度）。总线最后顶到 -1dBFS：游戏里 BGM 走「音乐」滑块能单独调，不需要预留余量——留 6dB
余量的交响乐听感只会像背景音。

作曲与渲染都由 tools/compose_commander_bgm.py 完成 —— 脚本内自带加法合成器（各音色就是一张谐波表）
与多抽头延迟混响，不依赖 SoundFont 或任何外部音源。改曲子只需改脚本里的乐谱表再重跑，会同时产出：
tools/commander_bgm.mid（标准 MIDI，18 轨，可在 DAW 里换音源重新渲染）、
tools/commander_bgm_preview.wav（试听用）与 mod 实际播放的 sounds/zombie_commander_bgm.ogg。
音轨在 sounds.json 里标了 stream 做流式解码，不会把整首长音轨常驻内存。
嫌鼓太满/太吵：把脚本 main() 里 render_kick / render_hihat / render_snare 的 gain 调小即可。

顺带修掉一个 MIDI 格式缺陷：`_track()` 写 track_name 时漏了开头的 delta-time（原本是 `FF 03 len text`，
正确应为 `00 FF 03 len text`）。SMF 里 meta 事件和普通事件一样必须以 delta 开头，漏掉会让 0xFF 被当成
变长量的首字节（0xFF 0x03 解成 delta = 16383），整条轨的事件流从第一个事件起全部错位、轨名读不出来。
修复后 18 条轨名全部可解析；反向对照（删掉那个 0x00）确认它会立刻失败。

修复 gametest 随机红：场地模板 + 弹丸用例改成确定性驱动
收尾「骨架动画 + 近战三段连招」时挖掉了一个一直在制造随机失败的地基问题。

根因：template = "empty" 指向的空模板只有 3x3x3（data/dreamingfishcore/structure/empty.nbt），
而框架的 StructureUtils.forceLoadChunks 是按「模板包围盒」去 setChunkForced 的 —— 于是只有
结构原点所在的那一个区块被强制加载。结构原点落在区块内的偏移每次运行都随机，场地事实上横跨
两个区块；隔壁区块只是被 setBlock 顺带加载进来、chunkVisibility 里没有登记（该登记由 ChunkMap
在每个 tick 回调写入）→ 落到那里的实体会被当成「不可见 / 不可 tick」：addFreshEntity 返回 true，
但 ServerLevel#getEntity(uuid) 与 getEntitiesOfClass(AABB) 都查不到它。实测到的症状：
护卫台账误判护卫已死（护卫两条用例偶发红）、连发用例数不到弹丸（战斗 Goal 用例偶发红）、
弹丸飞过区块边界后以 UNLOADED_TO_CHUNK 被清掉（弹丸命中用例红）。

修复：
- 新增 tools/make_test_structure_nbt.py，生成 data/dreamingfishcore/structure/commander_arena.nbt
  （24x24 全空气模板，只提供包围盒，场地仍由测试自己 setBlock）；ZombieCommanderGameTest 的
  九个用例改用 @GameTest(template = "commander_arena")。模板名不能带命名空间 —— 框架会自动加
  modid: 前缀，写成 dreamingfishcore:commander_arena 会得到 dreamingfishcore:dreamingfishcore:...
  直接崩服。
- 弹丸命中的用例改成手动 spike.tick() 把它驱动到命中，不再交给世界 tick；靶子挪到 1 格内。
  骨刺的飞行只用自身的 delta movement + 重力 + 自带扫掠、不读 gameTime，所以手动 tick 与真实
  飞行等价；这样既不再依赖区块状态，也不再依赖框架的逐 tick 驱动（代价是要自己补
  helper.succeed()）。
- 连发用例的失败信息补上「Boss 是否被移除 / 是否还在关卡实体表 / 场地内骨刺总数（不按 owner
  过滤）」—— 下次它红了会自己带证据，不必重跑复现。

验证：gradlew runGameTestServer 连续 10 轮 All 50 passed（修复前：弹丸命中用例 31 轮里红 13 次、

尸潮指挥官：军刀没握在手上（修复）

根因：转换链路把「骨骼自带的自转」整条丢掉了。bbmodel 里 saber 骨骼绕 x 转了 105°（刀尖前指），
而 convert_archer_zombie.py 生成 PartPose 时只读了骨骼的 origin、完全无视 group 的 rotation ——
于是军刀成了一条「位置对、角度归零」的骨骼：进游戏后刀身顺着小臂垂直扎向地面，看着就不像被手握着。
这种丢失完全静默：能编译、能加载、日志一个字都没有。bbmodel 的预览图和动画 GIF 反而是对的
（它们直接读 bbmodel），所以只有进游戏才看得出来。

修复：
- convert_archer_zombie.py 新增 _group_pose()：带自转的骨骼改用 PartPose.offsetAndRotation，
  角度沿用既有的 bedrock -> java 换算（x 保持、y / z 取反）。
- convert_commander_model.py 的 mirror_z() 补上「骨骼自转也要镜像」（绕 z 镜像时 x / y 取反、
  z 保持）—— 少了这一步，那份「已镜像」的文档会把 105° 算成反向、刀朝背后去；顺带修正
  element rotation 的镜像规则（此前写的是取反 z，本模型暂无带旋转的立方体，属潜在坑）。
- 转换脚本加硬拦：bbmodel 里任何带自转的骨骼，若生成的代码里没落到 offsetAndRotation，
  直接报错退出、不写文件。

验证：
- 新增 src/test/.../ZombieCommanderPoseTest：不看源码文本，把 createBodyLayer() 真烘一遍再断言
  saber.xRot = -105°、枢轴落在小臂下半段（手的位置）、刀尖必须指到身前。
- 反向对照：把生成物改回 offset(...)（旧行为）后，三条里恰好那两条相关的变红，报的正是
  「军刀的自转被丢掉了…expected: <-1.8325957> but was: <0.0>」与「刀尖应当指到身前…实际 z=0.0」；
  「枢轴在手的位置」保持绿（位置本来就没坏），说明断言是定点而不是连坐。

  逐立方体比角点 —— 22/22 个部件最大偏差 0.000 像素；同一脚本在缺陷版上只会挑出那 6 块军刀部件
